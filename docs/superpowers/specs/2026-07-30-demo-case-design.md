# Demo case seeded on first login — design

*2026-07-30*

## Goal

Every user finds a ready-made case the first time they log in: a realistic but
fabricated investigation whose data exercises every analysis tool Vestigo ships,
carrying the annotations, tags, views, dispositions and a story a real analyst
would have left behind. Users upgrading from an earlier version receive it once
at their next login. It can be deleted at any time, like any other case, and does
not come back on its own.

## Decisions

| Question | Decision |
|---|---|
| Ownership | Per-user private copy — each user gets their own case and can edit or delete it without affecting anyone else |
| Delivery | Prebuilt `.vestigo` archive committed to the repo, restored through the existing `transfer/importer.py` |
| Timestamps | Fixed absolute dates, no rebasing at import |
| Embeddings | Out of scope — Qdrant vectors are not portable through the archive |
| Operator control | New `demo_case_enabled` setting, default on |
| Seed timing | Background `JobStore` job dispatched after login, never blocking it |
| Size | ~250k events, 4 sources, 30 days |
| Tone | Realistic case with analyst-voiced notes and one explanatory story — no per-detector meta-labels |

## 1. Seeding mechanism

**Trigger.** `core/demo_case.py::maybe_seed_demo_case(user, store, jobs)` is called
at every session-creation point — local login (`api/routers/auth.py:99`) and the
OIDC callback — so both auth paths behave identically. It runs after the session is
issued and can never block or fail a login.

**Gate.** Seeds when both hold:

- `settings.demo_case_enabled` is true. New field in `core/config.py` with a
  matching `SettingSpec` in `core/settings_registry.py` (group "Onboarding",
  default `true`, editable in the admin console, not `env_only`, no restart
  required).
- `user.demo_case_seeded_at` is null.

**Flag.** New nullable `users.demo_case_seeded_at` timestamp column, added as an
autogenerated Alembic revision. Existing rows are null, so the upgrade backfill is
the same code path as a first login — there is no separate migration logic. The
column is stamped *before* the job is dispatched, so a failing import cannot make
every subsequent login re-dispatch.

**Execution.** `JobStore.create(kind="demo_seed")` runs `transfer.importer.import_case()`
against the packaged archive with the logging-in user as owner. It surfaces in the
normal job tray. Import failure already deletes the partial case, so a failure leaves
a clean case list plus a failed job row.

**Lifecycle.** Deletion is ordinary case deletion — no special path — and the case
never returns, because the flag stays stamped. `POST /api/demo/seed` re-dispatches
the same job on demand, surfaced as "Restore demo case" in the case-list empty state,
so deleting is not a one-way door.

## 2. The dataset

**Window.** Fixed `2026-05-01 → 2026-05-30`. Days 1–23 are the baseline; days 24–30
carry the intrusion, split into four labeled suspect windows (recon, foothold,
lateral, exfil) on a single baseline definition — the 1-baseline + 1..N-suspect
shape the model already supports.

**Sources (~250k events):**

| Source | Format | ~Events | Content |
|---|---|---|---|
| `winsec-workstations.csv` | Plaso CSV (EVTX-derived) | 90k | 4624/4625/4672/4688/7045 across 12 workstations and 2 domain controllers |
| `linux-auth.jsonl` | generic JSONL | 60k | sshd, sudo, cron, systemd on 6 servers, with free-text syslog messages |
| `proxy.csv` | generic CSV | 70k | host, url, `bytes_out`, `bytes_in`, user_agent, status |
| `fw-netflow.csv` | generic CSV | 30k | src, dst, port, bytes, duration, action |

**Timelines.** *Endpoint* (Windows + Linux), *Network* (proxy + netflow), *Full
incident* (all four), so timelines-as-grouping is demonstrated rather than implied.

**Scenario.** Contractor account `m.okonkwo` is compromised by a password spray from
a VPN pool, gains a foothold on a jump host, a service is installed for persistence,
the account moves laterally to a file server, an archive is staged, and it is uploaded
slowly to a file-sharing host.

### Detector coverage

Every signal is a by-product of the story. Nothing in the data is labeled with the
detector it triggers.

- **1 Value novelty** — never-before-seen 7045 service name; the contractor logging
  in from workstations absent from the baseline. *value_combo*: (user, host) pairs
  never seen before.
- **2 Frequency** — 4625 volume spike during the spray; a silence when the jump host
  stops logging for six hours on day 26.
- **3 Timestamp order** — one Linux host with NTP drift emits a few dozen out-of-order
  records. Benign, and that is the point.
- **4 Numeric range** — `bytes_out` far out of band during exfil; netflow duration
  outliers on the beacon.
- **5 Charset novelty** — staged archive filename containing a Cyrillic homoglyph;
  one user_agent with never-seen punctuation.
- **6 Entropy** — base64-encoded PowerShell in 4688 command lines; a long random
  subdomain in the proxy `host` field.
- **7 Proportion shift** — the file-sharing destination's share of proxy traffic
  jumps; the sudo command mix shifts on the file server.
- **8 Interval cadence** — a 300s ± jitter beacon on a host whose baseline was
  irregular human browsing, plus a backup cron whose cadence legitimately changes,
  giving one benign hit alongside the malicious one.
- **9 Event sequences** — a never-seen per-host ordering: failed-logon run, success,
  service install, outbound connection.
- **10 Value-distribution drift** — `bytes_out` shape change and a categorical share
  drift across a whole field.
- **11 Semantic similarity** — deliberately out of scope. Qdrant vectors do not survive
  the archive round-trip (`transfer/importer.py`: "vectors are not portable").
- **12 Repeating sequences** — the beacon motif, and a benign nightly backup motif so
  motif mining does not read as a malware-only tool.
- **13 Sigma** — four case-scoped `SigmaRule` rows ship inside the archive: encoded
  PowerShell, suspicious service install, wmic lateral movement, spray threshold.
- **14 Log templates** — syslog free text clusters into roughly 40 templates, one rare
  new template appearing only in the suspect window.

### Analyst artifacts in the archive

Roughly 25 annotations written in an analyst's voice; tags (`lateral-movement`,
`exfil`, `to-verify`, `benign-explained`); 5 saved Views; 2 saved charts; the baseline
definition with its four suspect windows; mixed dispositions on pre-run findings —
some `confirmed`, some `dismissed`, some `normal` — so the normality model is visible
without commentary; and one Story walking the incident end to end.

Baseline definitions and saved Views are included even though the case carries no
meta-labels: they are artifacts a real analyst leaves behind, and without a declared
baseline window the temporal detectors (1, 2, 7, 8, 10) have nothing to run against.

## 3. Building the archive

The generator lives in `tools/demo_case/` (outside the shipped package) and its output
is committed. It uses a seeded PRNG and the fixed date window, emits the four source
files and the metadata rows, drives the real ingestion pipeline against a throwaway
database, then calls `exporter.export_case()` to produce
`src/vestigo/assets/demo/demo-case.vestigo`.

Building runs through the real pipeline rather than writing ClickHouse rows directly,
so everything the demo case contains is reachable by an ordinary ingest.

Regeneration is a deliberate act — `uv run python -m tools.demo_case.build` — performed
at releases, not by CI on every commit, so the committed blob changes rarely.

Packaging needs no change: `pyproject.toml:81` packages `src/vestigo` wholesale, and
`src/vestigo/assets/converters` is already 1.6 MB of shipped assets, so the archive
reaches airgapped installs the same way.

The archive records the archive-format version the importer already validates. A test
imports it on every run, so a schema change that breaks it fails CI rather than
silently shipping a broken demo.

## 4. Verification

- **Import round-trip** — seed the archive into a test database; assert case, source,
  timeline, annotation, view, story and Sigma-rule counts.
- **Detector coverage** — run each of the 13 in-scope tools over the demo case's
  declared baseline and assert each returns at least one finding above threshold. This
  is the test that keeps the feature's promise true as detector math evolves: retuning
  a threshold until the demo goes quiet becomes a CI failure.
- **Seeding lifecycle** — null flag dispatches a job and stamps the flag; a second
  login dispatches nothing; the setting off dispatches nothing; a deleted case does not
  re-seed.
- **Auth parity** — the OIDC callback seeds identically to local login.

## 5. Risks

- **Repo weight.** The prebuilt archive adds roughly 10–15 MB to git history per
  regeneration, permanently. Accepted deliberately; the mitigation is regenerating only
  at releases.
- **Per-user duplication.** 250k events per user in ClickHouse — 12.5M demo rows at 50
  users. Documented for operators next to the setting.
- **Aging dates.** The fixed May 2026 window looks stale in a couple of years.
  Regenerating with a shifted window at any release fixes it.
- **Detector drift.** Addressed by the coverage test; without it this design rots
  quietly.
